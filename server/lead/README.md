# Приёмник заявок: сайт → бот MAX

Принимает заявку с формы и отправляет её ботом в MAX, в чат школы. Сайт
собран статикой и лежит на GitHub Pages — серверного кода там нет, поэтому
форма обращается сюда по HTTPS.

```
форма → POST на приёмник → проверка → бот MAX → чат школы
                                    ↓
                           номер заявки → «Заявка принята» + цель lead_delivered
```

Ключевое: **`lead_delivered` уходит только после ответа приёмника**. Если MAX
не принял сообщение, родитель видит ошибку и прямые контакты, а не «спасибо».
Из-за этого в отчётах Метрики видно ровно то, что школа реально получила.

## Где это работает

Развёрнуто на **Yandex Cloud Functions** (каталог `default`, функция
`primeswim-lead`). Выбрано за цену: бесплатного тарифа — миллион вызовов в
месяц — хватает с многократным запасом, счёт нулевой. Постоянно работающий
сервер ради нескольких заявок в день не нужен.

Юрисдикция здесь не придирка: заявка содержит персональные данные, а ч. 5
ст. 18 152-ФЗ требует обрабатывать данные граждан России на серверах в
России. Приёмник ничего не хранит, но принимает и передаёт — спорить с РКН
о том, считается ли это «накоплением», дороже, чем сразу взять площадку в
нужной юрисдикции. По той же причине не подходят Cloudflare Workers, куда
такое кладут по привычке.

Код от площадки не зависит. Вся логика в `handler.ts`, а входов два:

| Файл | Куда |
|---|---|
| `index.ts` → `dist/index.js` | **используется сейчас**: Yandex Cloud Functions и другие бессерверные площадки |
| `http.ts` → `dist/server.js` | обычный процесс: Timeweb Cloud Apps, VPS, docker — если однажды понадобится |

Переезд между ними стоит смены команды запуска, а не переписывания.

## Перед установкой

1. Бот создан через **@MasterBot** в MAX, токен получен.
2. Заведён чат, куда будут падать заявки, и бот в него добавлен. Можно и в
   личку — но отдельный чат переживает смену телефона, и в него можно
   добавить второго человека, не трогая настройки приёмника.
3. Кто-то написал в этот чат хотя бы одно сообщение — иначе бот не увидит
   события и не удастся узнать `chat_id`.

Узнать идентификатор:

```bash
node scripts/max-chat-id.mjs
```

Токен берётся из переменной окружения `MAX_BOT_TOKEN` и никуда не
сохраняется. На Windows: `$env:MAX_BOT_TOKEN='...'; node scripts/max-chat-id.mjs`
— после настройки почистите историю PowerShell.

## Как развёрнуто сейчас

Функция `primeswim-lead` в каталоге `default`, адрес вызова:

```
https://functions.yandexcloud.net/d4emnb0f0olh64dqj46r
```

| Параметр | Значение |
|---|---|
| Среда выполнения | `nodejs22` |
| Точка входа | `index.handler` |
| Таймаут | 15 секунд |
| Память | 128 МБ |
| Публичная функция | включена |

Развёртыванием занимается сервисный аккаунт `primeswim-deploy` с ролью
`editor` на каталог. Роли `admin` у него намеренно нет: включить публичный
вызов он не может, и это делается в консоли один раз при создании функции.
Ключ поменьше прав — ключ, которым меньше можно навредить.

### Переменные окружения функции

| Переменная | Обязательна | Что это |
|---|---|---|
| `MAX_BOT_TOKEN` | да | токен бота от @MasterBot. **Секрет.** Только здесь |
| `MAX_CHAT_ID` | да, если нет `MAX_USER_ID` | чат, куда падают заявки |
| `MAX_USER_ID` | нет | личка вместо чата |
| `ALLOWED_ORIGINS` | нет | через запятую. По умолчанию `https://www.primeswim.ru,https://primeswim.ru` |
| `MAX_API_BASE` | нет | по умолчанию `https://platform-api2.max.ru`. Домен API уже менялся один раз, поэтому вынесен наружу |

Токен бота не должен попадать в репозиторий, в переменные GitHub Actions и
никуда с префиксом `NEXT_PUBLIC_` — последнее означало бы, что он напечатан
в исходнике каждой страницы сайта.

### Обновить код функции

```bash
npm run build:lead
```

и залить получившийся `server/lead/lead-function.zip` новой версией: в
консоли — *Редактор → Загрузить ZIP-архив*, или через API авторизованным
ключом сервисного аккаунта. Каждая заливка создаёт новую версию; переменные
окружения задаются вместе с версией, а не отдельно от неё.

### Подключение сайта

Адрес функции лежит в переменной репозитория `LEAD_ENDPOINT` (GitHub →
*Settings → Secrets and variables → Actions → Variables*), оттуда воркфлоу
подставляет его в сборку. Секретом адрес не является: он и так виден в коде
страницы. Пока переменной нет, форма показывает честную ошибку и прямые
контакты.

## Если однажды переезжать

Логика от площадки не зависит, меняется только вход.

**Обычный хостинг (Timeweb Cloud Apps, VPS, docker).** Собрать
`npm run build:lead`, запускать `node server/lead/dist/server.js`. Приложение
слушает `PORT` (иначе 8080), отвечает `ok` на `GET /health` и аккуратно
завершается по `SIGTERM`, так что передеплой не рвёт запросы. На Timeweb Apps
это команда сборки `npm ci && npm run build:lead`, команда запуска — строка
выше, порт 8080. На VPS — systemd плюс nginx или Caddy для HTTPS.

**Другая бессерверная площадка.** Тот же архив, entrypoint `index.handler`.

## Проверка

С чужого адреса — должен быть отказ:

```bash
curl -i -X POST https://functions.yandexcloud.net/d4emnb0f0olh64dqj46r -H 'content-type: application/json' -d '{}'
```

Ожидаемо `403`: без разрешённого `Origin` заявки не принимаются.

Настоящая проверка — с сайта: заполнить форму и убедиться, что сообщение
пришло в чат. Тестовую заявку в чате видно сразу, её же номер показан
родителю на экране.

Локально, без хостинга и без MAX: поднять заглушку MAX на любом порту,
запустить `node server/lead/dist/server.js` с `MAX_API_BASE`, указывающим на
неё, и `ALLOWED_ORIGINS=http://localhost:3000`, а в `.env.local` сайта
прописать `NEXT_PUBLIC_LEAD_ENDPOINT=http://localhost:8080/lead`. Так
проверяется вся цепочка, включая экраны успеха и ошибки, без единого запроса
наружу.

## Что приёмник отвечает

| Код | Когда | Что видит родитель |
|---|---|---|
| 200 | заявка ушла в MAX | «Заявка принята», номер |
| 200 + `duplicate` | повтор с тем же ключом | то же, вторая заявка не создаётся |
| 400 | поля не прошли проверку | ошибки под полями, теми же словами, что в форме |
| 403 | запрос не с сайта школы | — |
| 413 | тело больше 8 КБ | — |
| 429 | слишком часто | «слишком много заявок подряд», прямые контакты |
| 502 | MAX не принял сообщение | «не получилось передать», прямые контакты |
| 503 | не заданы токен или получатель | «приём заявок временно не работает», прямые контакты |

`GET /health` отвечает `ok` и в этой таблице не участвует — он для площадки,
а не для посетителей.

## Персональные данные

Заявка нигде не сохраняется: она уходит в MAX и забывается. В логи идут
только статус доставки и номер заявки — ни имени, ни телефона, ни возраста,
ни комментария. Это проверяется тестом (`handler.test.ts`).

Смысл не в аккуратности, а в том, чтобы не заводить базу персональных данных
там, где она не нужна: нет базы — нечему утечь, нечего локализовать и не за
что получить оборотный штраф.

Правовая часть (уведомление в РКН, политика, согласие) разобрана в
`docs/legal-checklist.md`.

## Границы решения

Честно о том, чего здесь нет.

- **Лимит частоты и защита от повторов живут в памяти процесса.** Перезапуск
  их обнуляет, при нескольких экземплярах счётчики у каждого свои. Это
  заслон от случайного дубля и примитивного скрипта, но не от распределённой
  атаки. Настоящий лимит потребовал бы внешнего хранилища — дороже, чем
  проблема, которую он решает при нескольких заявках в день.
- **Повторов доставки от сайта нет.** Повторяет только приёмник и только
  запрос в MAX. Родитель может нажать «Отправить» ещё раз — ключ запроса тот
  же, и вторая заявка не создастся.
- **Очереди нет.** Если MAX недоступен все три попытки, заявка теряется, и
  родитель видит это сразу.
- **Заявка не попадает в CRM.** Только в чат MAX. Офлайн-конверсии
  (`trial_booked`, `subscription_paid`) — отдельная задача.
