# Доставка заявки: что есть сейчас и что нужно построить

Записка к следующему этапу. Сам этап **не реализован** — здесь только разбор
текущего состояния и требования к решению. Ничего из описанного ниже в коде нет.

Дата: 31 августа 2026.

## 1. Что происходит сегодня

```
форма → проверка в браузере → window.open(Telegram с текстом) → родитель жмёт «Отправить» → школа получает сообщение
```

Сайт собран статикой (`output: 'export'`, GitHub Pages), серверных обработчиков
нет. Форма ничего не передаёт: она собирает сообщение и открывает Telegram с уже
набранным текстом.

Что из этого следует:

- школа **не знает** о родителях, которые дошли до формы и закрыли Telegram;
- сайт **не может** подтвердить доставку — ни родителю, ни в аналитике;
- на устройстве без установленного и авторизованного Telegram сценарий рвётся;
- зато сайт **не получает персональных данных вообще** — это реальное
  преимущество текущей схемы, и терять его без причины не стоит.

Цель аналитики называется `open_telegram_draft` именно поэтому. Раньше
отправлялась `lead_submitted`, и каждое открытие черновика считалось заявкой:
число лидов в Метрике было завышено, а CPL — занижен.

## 2. Что должно появиться

```
форма → проверка в браузере → POST на endpoint → проверка на сервере → доставка в Telegram/MAX/CRM → ответ с номером заявки → lead_delivered
```

Ключевое отличие: **`lead_delivered` отправляется только после ответа
принимающей стороны**, а не по клику. Пока такого ответа нет, цели в проекте
быть не должно.

## 3. Требования к endpoint

**Размещение.** GitHub Pages не выполняет серверный код, и создавать
`app/api/*` route нельзя — при `output: 'export'` сборка его не соберёт.
Варианты: отдельная функция на стороннем runtime, к которой сайт обращается
по HTTPS, либо перенос хостинга. Решение о хостинге — отдельное, не побочный
эффект этой задачи.

**Секреты.** Токен бота и chat_id живут только в переменных окружения на
сервере. В репозиторий, в клиентский бандл и в `NEXT_PUBLIC_*` они не попадают
ни при каких условиях.

**Валидация на сервере.** Повторить правила из `src/lib/lead-schema.ts` — он
написан так, чтобы использоваться с обеих сторон. Клиентскую проверку считать
удобством, а не защитой: запрос можно отправить и мимо формы.

**Honeypot.** Поле `hpx7` уже есть в схеме. Имя намеренно бессмысленное:
предыдущее (`company`) заполняло автозаполнение браузера, и форма принимала
живого родителя за бота. Любое новое скрытое поле проверять на то же самое.

**Rate limit.** По IP и по нормализованному телефону. Порог подобрать по
реальному трафику, а не по умолчанию из примера.

**Идемпотентность.** Ключ запроса на клиенте, чтобы повтор при плохой сети
не создавал вторую заявку.

**Retry.** Только на стороне сервера и только для доставки в мессенджер/CRM.
Повторять POST от клиента без идемпотентности нельзя.

**Timeout и понятная ошибка.** Если доставка не удалась, родитель должен
увидеть это и получить запасной путь — телефон и прямые ссылки на мессенджеры.
Показывать «Спасибо» при неудаче нельзя.

**Журналирование.** Факт и статус доставки — да. Имя, телефон, возраст и
комментарий в логи — нет.

## 4. Аналитика после запуска

| Цель | Когда отправлять |
|---|---|
| `start_form` | первое касание поля, один раз на экземпляр формы — **уже есть** |
| `open_telegram_draft` | форма открыла черновик — **уже есть**, останется для запасного пути |
| `lead_delivered` | сервер подтвердил доставку — **добавить на этом этапе** |
| `trial_booked`, `trial_visited`, `subscription_paid` | из CRM как офлайн-конверсии |

Персональные данные в параметрах целей не передаются ни в одном случае.
UTM, `yclid` и посадочную страницу сохранять можно и нужно.

## 5. Юридическое — за пределами кода

- Появление сервера-приёмника меняет схему обработки: школа начинает получать
  персональные данные через сайт, а не только напрямую в мессенджере. Политику
  и, возможно, уведомление в РКН нужно пересмотреть **до** запуска.
- Свободный комментарий остаётся местом, куда родитель может написать сведения
  о здоровье ребёнка. Предупреждение в форме есть, но серверное хранение таких
  данных — отдельный режим (ст. 10 152-ФЗ). Проще не хранить комментарий
  дольше, чем нужно для ответа.
- Формулировки в форме и политике проверяет профильный юрист. Код здесь ничего
  не решает.
