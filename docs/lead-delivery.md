# Доставка заявки: как это работает

Дата последней правки: 3 сентября 2026. Этап **реализован** — заявка с формы
уходит ботом в MAX. Приёмник работает в Yandex Cloud Functions; установка
описана в `server/lead/README.md`,
здесь — решение целиком и его границы.

## 1. Как было

```
форма → проверка в браузере → window.open(Telegram с текстом) → родитель жмёт «Отправить»
```

Форма ничего не передавала: собирала сообщение и открывала Telegram с уже
набранным текстом. Из этого следовало:

- школа **не знала** о родителях, которые дошли до формы и закрыли Telegram;
- сайт **не мог** подтвердить доставку — ни родителю, ни в аналитике;
- на устройстве без установленного Telegram сценарий рвался;
- зато сайт **не получал персональных данных вообще**.

Цель называлась `open_telegram_draft` именно поэтому: считать открытый
черновик заявкой означало завышать число лидов и занижать CPL.

## 2. Как стало

```
форма → проверка в браузере → POST на приёмник → проверка на сервере →
  бот MAX → чат школы → ответ с номером заявки → lead_delivered
```

Родителю мессенджер больше не нужен: он заполняет форму и получает номер
заявки. Школа получает сообщение в MAX и видит номер там же.

Что мы за это отдали, честно: **сайт начал получать персональные данные.**
Раньше переписка шла напрямую между родителем и школой, теперь заявка
проходит через приёмник оператора. Он ничего не хранит и не пишет в
логи, но обработка появилась — и это отражено в политике и в уведомлении
в РКН (`docs/legal-checklist.md`).

## 3. Что где лежит

| Файл | За что отвечает |
|---|---|
| `src/components/sections/LeadForm.tsx` | форма, проверка в браузере, экраны успеха и ошибки |
| `src/lib/lead-schema.ts` | правила проверки — **общие для браузера и сервера** |
| `server/lead/handler.ts` | приём, повторная проверка, ловушка, лимит, идемпотентность |
| `server/lead/max.ts` | Bot API MAX: отправка, таймаут, повторы |
| `server/lead/message.ts` | текст заявки, который видит школа |
| `server/lead/http.ts` | HTTP-сервер: вход на Timeweb Cloud, VPS, docker |
| `server/lead/index.ts` | вход для бессерверных площадок — запасной путь |
| `scripts/build-lead-function.mjs` | сборка приёмника в один файл |
| `scripts/max-chat-id.mjs` | разовая настройка: узнать chat_id |

Правила проверки не продублированы. Клиентская проверка — удобство, а не
защита: запрос можно отправить и мимо формы, поэтому на сервере выполняется
та же `validateLead` из того же файла.

## 4. Требования и как они закрыты

| Требование | Как закрыто |
|---|---|
| Секреты не в репозитории | токен бота — только в переменных окружения приёмника; в `NEXT_PUBLIC_*` не попадает ничего, кроме адреса endpoint (он и так виден в коде страницы) |
| Валидация на сервере | `validateLead`, тот же модуль, что у формы |
| Honeypot | поле `hpx7`; имя бессмысленное намеренно — прежнее `company` заполняло автозаполнение браузера, и в ловушку попадали живые родители |
| Rate limit | по IP (5 / 10 мин) и по нормализованному телефону (3 / час) |
| Идемпотентность | ключ запроса на клиенте, один на экземпляр формы |
| Retry | только на сервере и только для запроса в MAX: 3 попытки, общий потолок 9 секунд |
| Timeout и понятная ошибка | при неудаче — сообщение и прямые контакты; «спасибо» не показывается |
| Журналирование | статус и номер заявки — да; имя, телефон, возраст, комментарий — нет, это покрыто тестом |

Пороги лимитов подобраны под масштаб школы, а не взяты из примера. Когда
накопится реальная статистика, их стоит пересмотреть по ней.

## 5. Границы

- Лимит частоты и защита от повторов живут **в памяти процесса**:
  перезапуск их обнуляет, а при нескольких экземплярах счётчики у каждого свои. Заслон от случайного дубля и простого скрипта,
  но не от распределённой атаки.
- Заявка **не попадает в CRM** — только в чат MAX.
- Если MAX недоступен, заявка **теряется**: очереди нет. Родитель видит это
  сразу и получает телефон и прямые ссылки на мессенджеры.

## 6. Аналитика

| Цель | Когда отправляется |
|---|---|
| `start_form` | первое касание поля, один раз на экземпляр формы |
| `lead_delivered` | **приёмник подтвердил доставку и назвал номер** |
| `click_phone`, `click_max_booking`, `click_telegram_booking` | в том числе с экрана ошибки |
| `trial_booked`, `trial_visited`, `subscription_paid` | из CRM как офлайн-конверсии, когда она появится |

`open_telegram_draft` и `lead_submitted` кодом больше не отправляются. В
кабинете Метрики они остаются ради истории — см. `metrika-goals.md`.

Персональные данные в параметрах целей не передаются ни в одном случае.
UTM, `yclid` и посадочная страница — можно и нужно.

## 7. Юридическое

Появление приёмника изменило схему обработки: школа получает персональные
данные через сайт, а не только напрямую в мессенджере. Что из этого следует
и что нужно сделать владельцу — в `docs/legal-checklist.md`.
